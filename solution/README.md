# TF-IDF candidate generator

Решение строит два локальных sparse-индекса по `benchmark_items.parquet` и для
каждого benchmark-запроса возвращает 50 объявлений. Оно не обращается к внешним
API, не использует тестовую разметку и детерминировано при зафиксированных
зависимостях.

## Подход

1. Word TF-IDF по униграммам и биграммам индексирует утроенный заголовок,
   параметры и описание объявления. В запрос дважды входит пользовательский
   текст и один раз текст фильтров.
2. Char TF-IDF по 3–5-граммам отдельно индексирует заголовки и помогает при
   опечатках, словоформах и слитном написании. Его вес равен `0.25`.
3. Кандидаты ограничиваются категорией запроса. Значение категории `0`
   преобразуется в `114`: все такие положительные пары в train относятся к
   категории услуг 114.
4. Совпадение `item_location_id` с `search_location_id` добавляет к score `0.7`.
   Это мягкий бонус, а не фильтр: около 17% положительных train-пар находятся в
   другой локации.
5. На случай менее 50 лексических кандидатов список детерминированно дополняется
   объявлениями той же локации/категории с наибольшим числом отзывов и рейтингом.

Конфигурация выбрана экспериментом `experiments/0005-word-char-tfidf`.
На двух локальных разбиениях по 2 500 запросов Recall@50 равен 0,5338 для cold
и 0,5615 для warm-запросов. Смесь 63/37, соответствующая доле новых и знакомых
текстов в benchmark, даёт ориентир 0,5440. Это локальная оценка, а не результат
публичного или закрытого leaderboard.

## Воспроизведение

Из корня проекта:

```bash
uv venv .venv
uv pip install --python .venv/bin/python -r solution/requirements.txt
.venv/bin/python solution/run.py
.venv/bin/python solution/validate.py
```

Первая команда создаёт локальное окружение, вторая устанавливает явно
зафиксированные open-source библиотеки NumPy, pandas, PyArrow, SciPy и
scikit-learn. Основной запуск читает три исходных Parquet-файла из
`assets/dataset/` и создаёт `answer.csv` в корне проекта. На машине Apple Silicon
пиковая память ожидается в пределах нескольких гигабайт; наиболее долгий этап —
построение полнотекстового индекса.

Отдельная проверка требует ровно две колонки, полный набор уникальных
`query_id`, не более 50 неповторяющихся `item_id` на строку и принадлежность
всех идентификаторов benchmark-корпусу.

## Что было проверено

- Константные popularity-baseline почти не работают (около 0,0007 Recall@50),
  а location-popularity даёт около 0,0313.
- Word TF-IDF по полному тексту с location-бонусом даёт около 0,4653.
- Добавление char-ветки поднимает ориентир до 0,5440.
- Рейтинг и доступность контактов оказались слабыми самостоятельными сигналами;
  они не используются в основном score. Отзывы и рейтинг применяются только в
  аварийном fallback, который не влияет на обычные запросы с текстовыми
  совпадениями.
